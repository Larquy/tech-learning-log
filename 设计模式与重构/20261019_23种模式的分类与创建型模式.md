# 23 种模式的分类与创建型模式（工厂方法·抽象工厂·单例·原型·建造者）

日期：2026-10-19　课程：设计模式与重构实践

> 接 2026-10-12《控制反转实现路径与六条设计原则》。前几讲一直在讲原则，这一章正式进入 23 种模式本身；本章只讲创建型 5 个，简单工厂只是引子（它不在 GoF 的 23 种里）。

## 一、23 种模式的两种分类方法

**分法一：按目的划分**（模式是用来完成什么工作）

| 类别 | 数量 | 干什么 | 名单 |
|---|---|---|---|
| **创建型** | 5 | 描述「怎样创建对象」，特点是**将对象的创建与使用分离** | 工厂方法、抽象工厂、单例、原型、建造者 |
| **结构型** | 7 | 描述如何把类或对象按某种布局**组成更大的结构** | 代理、适配器、桥接、装饰、外观、享元、组合 |
| **行为型** | 11 | 描述类或对象之间怎样**协作完成单个对象完成不了的任务**，以及职责怎么分配 | 模板方法、策略、命令、职责链、状态、观察者、中介者、迭代器、访问者、备忘录、解释器 |

**分法二：按作用范围划分**（主要作用在类上还是对象上）

- **类模式**：处理**类与子类**的关系，靠**继承**建立 → 编译期就确定，是**静态**的
  → 只有 4 个：**工厂方法、（类）适配器、模板方法、解释器**
- **对象模式**：处理**对象之间**的关系，靠**组合或聚合**实现 → 运行期可变，更**动态**
  → 除了上面 4 个，其余全是对象模式

记住这个「4 个例外」比背 23 个名字管用：类模式就是那 4 个，判断题基本都从这里出。

## 二、创建型模式要解决的共同问题

- 直接 `new` 的问题：构造参数一多，业务类里到处散落 `new`，**耦合过重**；后续构造方式一改，所有引用处都要跟着改
- 创建型模式的共同目标：**把「创建」和「使用」分开**，使用者只面向抽象
- 什么时候想到它：需要生成**复杂对象**（构造参数多、构造过程有步骤）的地方

下面 5 个模式的差别，本质是**「创建这件麻烦事，交给谁、怎么交」**的不同答案。

## 三、简单工厂：不在 23 种里，但是理解工厂的起点

**做法**：一个工厂类，里面一个**静态方法**，传参数（或传 `Class` 对象）进去，`switch`/`if` 判断后返回对应的产品对象。所以也叫**静态工厂方法模式**。

**三个角色**

- **简单工厂**（SimpleFactory）：核心，负责所有实例的创建逻辑
- **抽象产品**（Product）：所有产品的父类/接口，描述共有接口
- **具体产品**（ConcreteProduct）：真正被创建出来的目标

**典型代码骨架**

```java
public interface IProduct { void show(); }

static class SimpleFactory {
    public static IProduct makeProduct(int kind) {
        switch (kind) {
            case Const.PRODUCT_A: return new ConcreteProduct1();
            case Const.PRODUCT_B: return new ConcreteProduct2();
        }
        return null;
    }
}
// 客户端：只给参数，不问细节
IProduct p = SimpleFactory.makeProduct(Const.PRODUCT_A);
```

**课堂上还演进了两步**（这段是理解后续工厂方法的关键）

1. `create(String name)` 版本：按名字拼类名 → 新增产品要改 `create()` 里的判断，**违背开闭原则**
2. `create(Class<? extends ICourse> clazz)` 版本：**传 Class + 反射**创建 → 工厂不再关心具体类名
   → 再往前一步就是「**把类名写进 XML 配置文件，反射读出来**」，这正是工厂方法示例里 `ReadXML1` 干的事

**优点**

- 工厂类集中了判断逻辑，决定什么时候创建哪个产品；客户端**免除创建职责**，职责划分清楚
- 客户端只需知道参数，**不需要知道具体类名**
- 配合配置文件，可以在**不改客户端代码**的情况下更换/新增具体产品类

**缺点**

- 工厂类**单一、职责过重**：所有产品都它创建，一旦出问题整个系统受影响，代码容易臃肿，违背**高内聚**
- 增加了系统中的类个数，复杂度和理解难度上升
- **扩展困难**：新增产品必须**修改工厂里的判断逻辑**，产品一多逻辑就复杂 —— 这是它违背开闭原则的根子
- 工厂方法用了 `static`，**工厂角色无法形成基于继承的等级结构**

**应用场景**：产品种类相对较少时用它；客户端只要传参数就能拿到产品，不用关心创建过程。

> 📌 校对说明：课件第 14 页讲「简单工厂分析」时写的是「每增加一个产品就要增加一个具体产品类和一个对应的**具体工厂类**」，多了「具体工厂类」这一项 —— 那是**工厂方法**的特征。简单工厂只有一个工厂类，新增产品只在同一个工厂里加分支，这也正是它"违背开闭原则"的原因。按前一种说法理解。

## 四、工厂方法与抽象工厂

### 4.1 工厂方法：把「判断」也抽象掉

**基本思想**：简单工厂的进一步抽象化 —— 不再由一个工厂用 `if/else` 决定造什么，而是**每种产品配一个自己的工厂**。好处是新增产品时**只加类、不改原有代码**，满足开闭原则。

**四个要素**

| 角色 | 职责 |
|---|---|
| **抽象工厂**（Abstract Factory） | 提供创建产品的**接口**（`newProduct()`），调用者通过它访问具体工厂 |
| **具体工厂**（ConcreteFactory） | 实现抽象工厂的方法，真正造出具体产品 |
| **抽象产品**（Product） | 定义产品规范，描述主要特性和功能 |
| **具体产品**（ConcreteProduct） | 实现抽象产品接口，**与具体工厂一一对应** |

**课程示例（选课系统里那个课程例子）**

```java
public interface ICourse { void record(); }
public interface ICourseFactory { ICourse create(); }

public class JavaCourseFactory implements ICourseFactory {
    public ICourse create() { return new JavaCourse(); }
}
// 调用
ICourseFactory factory = new JavaCourseFactory();
ICourse course = factory.create();
course.record();
```

配合 XML 配置的做法：`DocumentBuilderFactory` 解析 `config1.xml`，取 `className` 节点，`Class.forName(cName).newInstance()` 反射出工厂对象 —— 换成 Python 课只改配置文件，客户端一行不动。

**优点**

- 只需知道**具体工厂的名称**就能拿到产品，无须知道创建过程
- 灵活性增强：新增产品**多写一个工厂类**即可
- 典型的解耦框架：高层模块只认识**抽象产品**，同时满足**迪米特法则、依赖倒置、里氏替换**

**缺点**

- 类的个数容易过多，增加复杂度
- 抽象性和理解难度上升
- **抽象产品只能生产一种产品** —— 这个弊端要靠抽象工厂解决

### 4.2 抽象工厂：一个工厂造一族产品

**定义**：为访问类提供一个**创建一组相关或相互依赖对象**的接口，访问类无须指定具体类，就能得到**同族不同等级**的产品。

**与工厂方法的结构差别**：要素还是那 4 个，但**抽象工厂里的方法不止一个，抽象产品也不止一个**。

```java
interface AbstractFactory {
    Product1 newProduct1();
    Product2 newProduct2();   // 关键：一个工厂多个产品方法
}
```

**产品族 vs 产品等级（这组词是这一节的考点）**

- **产品族**：同一个具体工厂造出来的那一组产品（同品牌、相配套）→ 换工厂 = 换整个品牌
- **产品等级**：同类产品的不同层级（如「动物」这一层、「植物」这一层）

**课堂实例：农场**。农场既要养动物（马、牛），又要种植物（菜、水果），两个产品等级 → 必须用抽象工厂。

**开闭原则上的「倾斜性」**

- 增加一个**新产品族**（新的品牌/农场）→ 只加一个具体工厂，**满足**开闭原则
- 给某个产品族**增加一个新种类的产品**（比如农场里再加「农机」）→ **所有工厂类都要改**，**不满足**开闭原则
- 系统中只剩一个等级结构的产品时，**抽象工厂退化成工厂方法**

### 4.3 三者怎么看

| | 简单工厂 | 工厂方法 | 抽象工厂 |
|---|---|---|---|
| 在 23 种里 | 不在 | 在（类模式） | 在（对象模式） |
| 工厂数量 | 一个工厂包全部 | 一产品一工厂 | 一产品族一工厂 |
| 新增产品要改旧代码吗 | 要改工厂判断逻辑 | 不用，加类即可 | 加产品族不用；加产品等级要改所有工厂 |
| 产品种类 | 一类 | 一类 | 多类（产品族） |

## 五、单例（Singleton）

**定义**：一个类**只有一个实例**，且该类能**自行创建**这个实例。

比如 Windows 只能开一个任务管理器：多开会浪费内存，还会出现各窗口显示内容不一致。回收站、打印后台服务、日志对象、数据库连接池、网站计数器、系统缓存通常都做成单例。

**两个角色**：单例类（含一个实例、能自行创建）、访问类（使用单例的类）。

**为什么要把构造器写成 private**：普通类构造器是 public，外部 `new` 一次就多一个实例；把构造器设为 private，外部就 `new` 不出来 → 只能由类自己维护一个**静态私有实例**，再对外提供**静态公有**的 `getInstance()` 来创建或取用。

**四种写法**

| 写法 | 关键点 | 线程安全 | 延迟加载 |
|---|---|---|---|
| **懒汉式**（同步方法） | `private static volatile` + `public static synchronized getInstance()` | 安全，但**每次访问都同步，性能差** | 是 |
| **双重检查锁** | `synchronized (LazySingleton.class)` 包住第二次判空 | 安全、性能比上面好 | 是 |
| **静态内部类**（LazyHolder） | 单例放在私有静态内部类里，调用 `getInstance()` 时才触发该内部类加载 | 安全（类加载机制保证） | 是，且兼得前两者好处 |
| **饿汉式** | `private static final` 直接 `new` 好，`getInstance()` 直接返回 | 安全（类加载即完成） | 否，可能白占内存 |

**懒汉式的两个关键字不能删**：多线程下删掉 `volatile` 和 `synchronized` 会出现线程不安全（可能造出两个实例）。

**饿汉式**：类一加载就建好单例，保证调用 `getInstance()` 之前实例已存在；以后不再改变，所以线程安全，可直接用于多线程。

**使用场景**

- 频繁创建、用完就丢的类：降低内存压力、减少 GC（线程池、连接池、网络连接池）
- 某类只允许一个对象：一个班只有一个班长、一个人只有一个身份标识
- 实例占用资源多、初始化耗时长，且经常使用
- 控制硬件级操作、或整个系统只应有单一控制逻辑的地方 —— 多个实例会让系统乱套
- 需要共享的对象：Web 配置对象、数据库连接池

**优点**：内存里只有一个实例，省内存；避免对资源的多重占用；提供全局访问点，便于共享和优化访问。

**缺点**

- 一般**没有接口**，扩展只能改原代码，违背开闭原则
- 并发测试时不利于调试：单例代码没跑完，也没法模拟生成新对象
- 功能代码常堆在一个类里，设计不当容易违背单一职责

## 六、原型（Prototype）

**定义**：用一个已创建的实例当**原型**，**复制**它来创建相同或相似的新对象。原型实例本身就指定了要创建的对象种类，**无须知道创建细节**，效率高。

**三个角色**：抽象原型接口（规定必须实现的接口）、具体原型类（实现 `clone()`，可被复制）、访问类（调 `clone()` 得到新对象）。

**clone 与 new 的区别**

- `new`：先按类型**分配内存** → 调**构造函数**填充各域（对象初始化）→ 返回引用
- `clone`：同样分配内存（大小与源对象相同）→ 但**直接用源对象的各个域填充**新对象 → 返回引用，**构造方法不执行**

**浅克隆 vs 深克隆**

- **浅克隆**：新对象属性值与原来完全相同，但**非基本类型属性仍指向原对象那块内存地址**
- **深克隆**：属性里引用的对象**也一起被克隆**，不再指向原地址

**课程里的实测例子（Person 里有 `int[] ints`）**

```java
Person clonePerson = (Person) person.clone();
ints1[0] = 50;                      // 改数组
clonePerson.setName("666666666");   // 改引用类型
// 结果：原对象 age、name 不变，但数组变成 50 2 3 —— 说明数组是浅拷贝
// person == clonePerson ? false    → 对象本体确实是新的一份
```

两个结论：**对象本体是新的一份（`==` 为 false），但内部引用类型还是同一块内存**。

**String 是特例**：虽然也是引用类型，但它是 **final 类**，又有**字符串常量池**，所以不必额外处理。

**深克隆的实现**：`clone()` 里自己 new 一个对象，把数组 `System.arraycopy` 复制一份再 `setInts()` 进去。

**优缺点**：内存里二进制流拷贝，比 `new` 性能好，尤其**大量对象**时；缺点是**直接内存拷贝，构造函数不执行**（构造里的校验、初始化副作用都会被跳过）。

## 七、建造者（Builder）

**定义**：把一个**复杂对象的构造**与它的**表示**分离，使同样的构建过程可以创建**不同的表示**。也就是把复杂对象拆成多个简单部件、一步步装配起来 —— **变与不变分离**：产品的组成部件不变，每部分可以灵活选择。

**采购电脑的比喻**：采购员不会自己装机，他把配置要求告诉销售公司，公司安排技术人员组装好再交付。

**四个角色**

| 角色 | 职责 |
|---|---|
| **产品**（Product） | 含多个部件的复杂对象，由具体建造者创建各零件 |
| **抽象建造者**（Builder） | 定义创建各子部件的抽象方法，通常还有返回产品的 `getResult()` |
| **具体建造者**（ConcreteBuilder） | 实现 Builder，完成各部件的具体创建 |
| **指挥者**（Director） | 调用建造者的部件构造与装配方法完成创建，**自己不涉及具体产品信息** |

**标准写法骨架**

```java
Builder builder = new ConcreteBuilder();
Director director = new Director(builder);
Product product = director.construct();   // 指挥者按固定步骤装配
```

**链式赋值那种写法（课件里的 House 例子）**

把 builder 写成**静态内部类**，每个 `setXxx` 返回 `this`，最后 `builder()` 才真正 `new House(this)`：

```java
House h = new HouseBuilder()
        .setBasics("地基10米")
        .setWall("砌墙0.5米")
        .setRoof("屋顶5米")
        .builder();
```

这种写法**省略了 Director 和抽象 Builder**，本质还是「分步设置 + 最后构建」。

**优点**：封装性好（构建与表示分离）；扩展性好（各具体建造者相互独立，利于解耦）；客户端不必知道产品内部组成，建造过程可逐步细化而不影响其他模块，便于控制细节风险。

**缺点**：产品组成部分必须相同，**限制了适用范围**；产品内部结构一变，建造者也要同步改，维护成本大。

**与工厂模式的分界**：**简单对象用工厂，复杂对象用建造者**。建造者的典型场景：

- 相同的方法、不同的执行顺序 → 产生不同结果
- 多个部件都能装进一个对象，但装配结果不同
- 产品类非常复杂，或调用顺序不同产生不同作用
- 初始化对象特别复杂、参数多、很多参数有默认值

**模式的扩展**：产品只有一种时，可以省略抽象建造者；只有一个具体建造者时，连指挥者也能省掉。

## 八、易错点与课堂口径

1. **简单工厂不属于 23 种 GoF 模式**，它只是工厂方法的引子 —— 别在"GoF 23 种"里数它
2. **类模式只有 4 个**：工厂方法、（类）适配器、模板方法、解释器；其余都是对象模式
3. **工厂方法 vs 抽象工厂**：抽象工厂的抽象工厂里有**多个**创建方法、抽象产品有**多个**，管的是**产品族**；只有一个等级时抽象工厂会退化成工厂方法
4. **开闭原则的倾斜性**：抽象工厂「加产品族」满足开闭，「加产品等级」不满足
5. **单例**：`volatile` + `synchronized` 是线程安全的保证、饿汉式不是懒加载、静态内部类靠类加载机制实现延迟加载
6. **浅克隆**：对象本体是新的，但内部引用类型仍共享同一块内存；判断标准是「改拷贝里的引用类型，原对象会不会跟着变」
7. **深克隆**：构造方法不会执行；这也意味着构造器里的校验/初始化逻辑被跳过
8. 建造者核心是**构造与表示分离**，能用工厂就别用建造者（复杂对象才用）

> 课件里另有两处笔误，看的时候留个心：第 4 页结构型那里写"GoF 中提供了 7 种**创建型**模式"（应为 7 种**结构型**）；第 37 页静态内部类懒汉式的示例代码括号和变量名有缺漏，那段照「把实例放进私有静态内部类、用类加载兜住线程安全」的思路理解即可，别照抄。

## 九、要点清单（考前扫一眼）

1. 按**目的**分：创建型 5、结构型 7、行为型 11；按**作用范围**分：类模式 4 个、其余对象模式
2. 类模式 4 个：工厂方法、类适配器、模板方法、解释器（靠继承、编译期确定）
3. 创建型模式的共性：**创建与使用分离**，用在构造复杂对象的地方
4. **简单工厂**：一个工厂 + 静态方法 + 分支判断；不在 23 种里；新增产品要改工厂逻辑，违背开闭
5. **工厂方法**：一产品一工厂，4 要素，新增产品只加类；抽象产品只有一种
6. **抽象工厂**：一工厂多产品，管产品族；加族可以、加等级不行；单等级时退化成工厂方法
7. **单例**：private 构造 + 静态私有实例 + 静态公有 getInstance；懒汉要 volatile+synchronized，静态内部类最优，饿汉最简单但不延迟
8. **原型**：clone 不走构造器；浅克隆只复制值、引用类型共享内存，深克隆要自己对引用类型再复制
9. **建造者**：构造与表示分离，Product/Builder/ConcreteBuilder/Director 四角色，复杂对象才用
