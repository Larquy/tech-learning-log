# 控制反转的实现路径与六条设计原则（接口·开闭·单一职责·接口隔离·迪米特）

日期：2026-10-12　课程：设计模式与重构实践

> 接 2026-09-21《依赖倒置原则》末尾留的那个问题（构造函数/Set/注解注入怎么选、容器帮我们做了什么），这次课正面回答了。

## 一、控制反转（IoC）到依赖注入（DI）的实现路径

**IoC 是原则，反射与容器是手段**

- **控制反转**是解决问题的**指导原则**，它本身不是技术；具体技术手段包括**动态反射创建对象**
- **动态反射**解决的是「对象创建」的**动态性**问题，但光有反射不够，还要**配合容器机制**才能完整落地

**容器与缓冲区**

- 做法：构建**容器**当作缓冲区，在**启动时**把对象初始化好并装进去
- 这顺带解释了一个现象：**Java / Spring 项目启动比较慢** —— 启动阶段在装配对象

**依赖注入是 IoC 衍生的初始化方式**

- 由控制反转原则衍生出**依赖注入**，具体方式有三种：**构造函数注入**、**Set 方式注入**、**注解注入**
- 框架对应关系：Java 生态对应 **Spring**；C# 生态对应框架（原笔记记作「LC 框架」，**存疑待核**）

## 二、接口与抽象类：适用场景不一样

| | 接口 | 抽象类 |
|---|---|---|
| 侧重 | **行为契约**：描述一组抽象行为，形成固定契约 | **生命实体**：表达有共同属性（学号、姓名）的鲜活实体继承关系 |
| 边界感 | 强，**修改不可接受** | 相对弱 |
| 典型用途 | 关注「学生 / 课程有哪些**行为动作**」时选它 | 关注「实体的**共性属性**」时选它 |

**语言差异会反过来影响选型**

- **C++ 没有 interface 关键字**，只能用抽象类模拟，**边界感较弱**
- Java / C# 中两者可以结合使用：**抽象类可以实现接口**（Java 里是 `implements`）

**落到选课系统上**：需要抽象「选课、退课、查成绩」这类**动作** → 用接口；需要表达「本科生与研究生共同有学号、姓名」→ 用抽象类。

## 三、开闭原则（OCP）

**对修改关闭**

- 已完成功能的代码不应直接修改，尤其是**接口已经对外提供服务**时（微信小程序、App、网页）
- 小系统、封闭系统可以不严格遵守；**涉及多方协作的互联网系统必须遵守**

**对扩展开放（两条实现方式）**

1. **继承覆盖原有方法**：子类重写父类方法实现新逻辑，不改动原函数
2. **新增业务类替代**：提供新的业务类供客户端调用，比如大促结束就停用新业务类，流程自动恢复

**一条硬约束**：受接口控制的类**不能直接在接口上加函数** —— 所以只能靠上面两种扩展方式绕开。

**前提条件**：开闭原则适用于**需要灵活性的模块交互场景**，不是所有代码都要机械遵守；如果改动**不影响任何模块、也没有外部依赖**，直接改就行。

## 四、单一职责原则（SRP）

**判断标准**

- 一个类或函数**只负责一项职责**；修改一个职责不应影响另一个职责
- 职责划分是**经验性判断**，核心目标是**降低复杂度、避免相互甩锅**

**从课程与用户类型看拆分**

- **直播课与录播课**分开：直播不支持快进快退、录播支持反复观看，处理方式不同 → 拆成两个类
- **用户类型细化**：普通、VIP、SVIP 在广告展示与权限上职责不同 → 各自独立处理

**交互设计里的体现（很直观的一个例子）**

- 旧模式：改用户名、地址要**点「确定」**，再弹窗提示成功或失败，操作约 **3 步**
- 新模式：改完**鼠标移开即自动保存**，只有失败时才提示，操作降到 **1 步多**
- 设计本质：把「**修改**」与「**确认**」两个职责**分离**，减少用户操作负担 —— 这就是单一职责落在交互层

## 五、接口隔离原则（ISP）

**先把「最小接口」理解对**

- 最小接口**不等于接口数量越少越好**，而是指从**不同角度分门别类**建立**专用接口**
- 用户**不应依赖它不需要的接口**；类应依赖在最小接口之上

**动物行为的典型案例**

- 错误做法：把飞、游、吃三个行为合并成一个 `Animal` 接口 → **不会飞的鸟被迫实现空方法**，调用时可能直接失败
- 正确做法：按行为拆成多个最小接口 —— 鸟类只实现「飞 + 吃」，狗类只实现「吃 + 跑」，避免空转与误用
- 关键认识：**接口是功能窗口**，看到接口就知道这个类具备哪些能力；**空方法会误导使用者**

**高内聚低耦合**

- 调用方只依赖**抽象接口**，无需知道实现类到底是 Bird 还是 Dog
- 接口隔离让每个接口职责单一，符合高内聚低耦合的设计思想

## 六、迪米特法则（LoD，最少了解原则）

**操作定义**

- 「**只跟朋友交流，不和陌生人说话**」，强调的是**强边界感**
- 但注意是「**尽可能少了解**」，**不是完全不说话** —— 底层的执行者仍要与必要对象交互

**谁是朋友、谁是陌生人**

| 类别 | 范围 |
|---|---|
| **朋友** | 成员变量、方法的输入输出参数、成员方法本身 |
| **陌生人** | 方法内部创建的**局部变量**、与自己**非直接关联**的对象 |

**Boss–Leader–Course 案例**

- 优化前：Boss 直接依赖 Course 对象拿统计结果，Course 成了 Boss 方法里的**陌生人**，信息传递冗余且容易出错
- 优化后：Boss **只向 Leader 请求结果**，Course 相关的处理逻辑封在 Leader 内部，Boss 不再接触 Course
- 价值：减少对象间耦合，降低信息传递出错的概率，系统更好维护

## 七、课堂练习与 UML 绘图规范

**选课系统设计作业**

- 业务对象：学生分**本科生 / 研究生**两类，课程分**本科课程 / 研究生课程**两类，**至少五个类**
- 交付物：**UML 类图 + 面向对象伪代码**（伪代码不强制可运行，重在表达设计思路）
- 时间：课堂留 **4~5 分钟**动手时间（原笔记记「5~4 分钟」，按上下文取 4–5 分钟），未完成者课间提交

**UML 类图的关键规范**

- **接口实现符号**：必须用**虚线 + 空心三角**，不可用实线或实心三角
- **类结构三要素**：每个类都要有**成员变量、构造函数、成员函数**三部分
- **关系要写全**：区分继承、接口实现、关联（可细分为聚合与组合）、依赖，**共六种**

**代码与类图要能双向转换**

- 既能把旧代码转成新类图，也能把新类图还原成代码
- 转换的过程本身就体现了「控制反转这些手段」与「设计目标」之间的对应关系

## 八、本篇要点清单（考前扫一眼）

1. **IoC 是原则，反射 + 容器是手段**；容器在启动时装配对象 → Spring 启动慢的原因
2. **DI 三种注入方式**：构造函数注入、Set 注入、注解注入；Java 对应 Spring
3. **接口管行为契约**（边界强、不可改），**抽象类管实体共性属性**；C++ 只能用抽象类模拟
4. **开闭原则**：对修改关闭（尤其对外服务的接口）、对扩展开放（继承覆盖 or 新增业务类）；接口上不能加函数
5. 开闭原则**有前提**：需要灵活性的模块交互才用它，无外部依赖的孤立改动可以直接改
6. **单一职责**看「改一个职责会不会牵动另一个」；直播/录播、普通/VIP 用户、修改即保存都是它的例子
7. **接口隔离**：最小接口 = 按行为分类的专用接口，不是数量少；避免被迫实现空方法
8. **迪米特法则**：只跟朋友（成员变量、参数、成员方法）交流，避开陌生人（方法内局部变量、非直接关联对象）
9. **UML 规范**：接口实现用虚线 + 空心三角；类要有成员变量、构造函数、成员函数；六种关系写全
