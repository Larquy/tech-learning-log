# 依赖倒置原则（DIP）

日期：2026-09-21　课程：设计模式与重构实践

## 结论先行

**高层模块不要自己 new 具体类；高层和低层都应该依赖抽象，具体类从外面传进来（依赖注入）。**

原话两条：① 高层模块不应该依赖低层模块，两者都应依赖抽象；② 抽象不应该依赖细节，细节应该依赖抽象。

## 1. 违反 DIP 的写法（课堂幻灯片那张图）

```java
public class Client
{
    Cup cup = new Cup();      // Client 直接制造具体类
    Man man = new Man();      // 同上
    man.drink(cup);           // Man 的 drink 又写死只收 Cup
}
```

类图关系：`Client → Man`、`Client → Cup`、`Man → Cup`（方法签名 `drink(Cup cup)`）。
**三条依赖全部指向具体类**，这就是问题所在。

## 2. 为什么不好

| 想改的需求 | 会牵动谁 |
|---|---|
| 换个人喝（女人 / 机器人） | Client 要改（写死了 `new Man()`） |
| 换成瓶子/保温杯喝 | Client 要改 **且** Man 的 `drink(Cup)` 签名要改 |
| 单元测试想用假的 Man | 做不到，被 `new` 绑死了 |

一句话：**客户端被具体的"人和杯子"焊死了，需求一变就要改调用方。**

## 3. 改成符合 DIP

```java
interface Drinkable { void fillWater(); }          // 抽象：能装水的东西
interface Person    { void drink(Drinkable d); }   // 抽象：能喝水的人

class Cup    implements Drinkable { public void fillWater(){...} }
class Bottle implements Drinkable { public void fillWater(){...} }
class Man    implements Person    { public void drink(Drinkable d){...} }

public class Client {
    private Person    person;      // 只依赖抽象
    private Drinkable drink;
    Client(Person p, Drinkable d) { person = p; drink = d; }   // 依赖注入
    void run() { drink.fillWater(); person.drink(drink); }
}
```

好处：换杯子（Cup→Bottle）、换人（Man→Robot）、换测试桩，**都不用改 Client**，只要在外面 new 好传进来。

## 4. 生活类比

Client 像"安排喝水的人"。
- 违反版：它必须**亲手去造一个男人和一个杯子**——人换了、杯子换了它就得重写流程。
- 符合版：它只说"**给我一个能装水的东西 + 一个能喝水的人**"，谁来、用什么杯子都行。

## 5. 踩的坑

1. "依赖抽象"不等于"到处写 interface" —— 只有**会被替换/需要测试**的地方才值得抽接口。
2. Java 里 `implements` 是"实现接口"，`interface` 只写方法签名、没有实现（对比 C++ 的抽象类/纯虚函数）。
